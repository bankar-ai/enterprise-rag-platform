# ADR-005 — BM25/Vector Fusion via Reciprocal Rank Fusion

Status: Accepted
Related Ticket: ERP-014

## Context

ERP-012 shipped vector-only (semantic) retrieval. ERP-014 adds BM25 lexical retrieval (via Postgres full-text search) as a second retriever, and the two ranked lists need to be combined into one. FAISS returns L2 distances (unbounded, lower-is-better) and Postgres `ts_rank` returns an unbounded, corpus-dependent relevance score (higher-is-better) — the two scales are not comparable, so a fusion method is needed that doesn't require normalizing raw scores onto a common scale.

Per `CLAUDE.md`'s "Research Before Recommending" rule, current practice was checked via web search rather than assumed from prior knowledge (see Sources below). Reciprocal Rank Fusion (RRF) is the consistently recommended approach for exactly this BM25+vector combination in current hybrid-search literature and production systems (Azure AI Search, Elasticsearch, Weaviate all document it as their default hybrid-search fusion method).

## Decision

Fuse BM25 and vector results using **Reciprocal Rank Fusion**: for each retriever, each document gets `1 / (k + rank)` (1-indexed rank within that retriever's result list; a document absent from a retriever's list contributes 0 for that term). Per-retriever contributions are summed, then normalized by the maximum achievable sum (rank 1 in every non-empty list) so the final score is bounded to `(0, 1]` — restoring the bounded-score contract ERP-012 established, without claiming the value is a similarity metric. Results are sorted descending by that normalized score. `k = 60`, the constant used in the original RRF paper (Cormack et al.) and the value most hybrid-search implementations default to — it dampens the influence of low ranks without needing to be tuned per corpus.

Each retriever is queried for `top_k * RRF_OVERSAMPLE_MULTIPLIER` candidates (multiplier `4`), not `top_k`. Fusing two lists that are each already truncated to `top_k` means RRF can only ever reorder their union (at most `2 * top_k` items) — a chunk ranked just outside `top_k` on one retriever but strong on the other would never get a chance to fuse into the result, which defeats the purpose of combining two signals. Oversampling before fusion, then truncating to `top_k` after, is standard practice in the production systems cited below (typically 2x–10x the final result count, or a fixed floor).

**Deploy-order note**: `search_chunks_by_text` depends on the `search_vector` column added by this ticket's Alembic migration. Environments must run `alembic upgrade head` before deploying app code built from this change — deploying the app first would make every `/retrieval/query` call fail with an `UndefinedColumn` error (surfaced as a 503) until the migration runs. This is a new deploy-ordering constraint ERP-012 didn't have.

## Alternatives Considered

- **Weighted linear combination of normalized raw scores** (e.g. min-max normalize FAISS distance and BM25 rank, then `score = alpha * vector_score + (1 - alpha) * bm25_score`) — rejected: requires choosing and justifying a normalization strategy and an `alpha` weight, both of which are corpus-sensitive and add a tuning knob with no principled default; RRF needs neither.
- **Vector-first with BM25 only as a tie-breaker** — rejected: doesn't actually combine the two signals, just uses BM25 to break ties among vector-equal results, which undersells the point of adding a lexical retriever (catching exact-term matches semantic search misses).
- **Cross-encoder reranking instead of fusion** — rejected as the mechanism for *this* ticket: reranking is explicitly ERP-015, a later, separate, optional post-processing step over whatever candidate list retrieval already produces (which itself needs to exist first, i.e. the fused BM25+vector list this ADR produces).

## Consequences

Scores returned by `RetrievedChunk.score` after this change are normalized RRF scores, not `1 / (1 + distance)` — still bounded `(0, 1]`, but `1.0` now means "ranked first in every retriever that found it," not "near-identical embedding." This is a behavior change to score *meaning* but not to the response *contract* (still a `float` in `(0, 1]`, still higher-is-better, still used purely for ranking, not compared across requests). Consumers that treat `score` as an opaque ranking signal are unaffected; anything relying on the specific `1/(1+distance)` formula or treating `score` as a raw similarity would need updating — `RetrievedChunk`'s field description now says so explicitly. RRF composes cleanly with ERP-015's reranking (an optional additional pass over the fused list) without requiring rework.
