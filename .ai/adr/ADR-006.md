# ADR-006 — Reranker Choice: FlashRank (ms-marco-MiniLM cross-encoder)

Status: Accepted
Related Ticket: ERP-015

## Context

ERP-015 adds an optional reranking pass over the fused (BM25+vector) candidate list ERP-014 produces. Per `CLAUDE.md`'s "Research Before Recommending" rule, current open-source/free reranker options were researched via web search rather than assumed from prior knowledge (this is a fast-moving area). The project's constraints: open-source/free only (`docs/architecture.md`), self-hosted/local (no paid reranking APIs — consistent with the existing Ollama-based approach), and "avoid dependency bloat" (`CLAUDE.md`'s Dependency Policy).

Two broad approaches were compared:

1. **A purpose-built cross-encoder reranker** (e.g. BGE-reranker-v2-m3, `ms-marco-MiniLM-L-6-v2`), run locally.
2. **LLM-as-reranker**: prompt the existing Ollama-hosted LLM (Qwen3) to score or reorder candidates — zero new dependency, since `ollama` is already a project dependency used for embeddings.

Current comparative evidence (see Sources): purpose-built cross-encoders like BGE-reranker-v2 score meaningfully higher on retrieval-quality benchmarks (NDCG@10 ~0.74) than general LLM-prompted reranking (~0.68 for a comparably-sized model), and run in milliseconds rather than adding a noticeable (~1s+) per-query LLM round trip. LLM-as-reranker also adds output-parsing complexity (extracting scores/order reliably from free-form generation) that a purpose-built model's numeric score output avoids entirely.

## Decision

Use **FlashRank** (`flashrank` PyPI package) with its default lightweight cross-encoder model (`ms-marco-MiniLM`-family, ONNX runtime, no GPU/torch required) as the reranking backend, invoked as an **optional** post-processing step (`RetrievalQuery.rerank: bool = False`) over the fused candidate list from `service.search`.

FlashRank was chosen over directly wiring in `sentence-transformers`' `CrossEncoder` because it depends only on `onnxruntime` + small helper libraries (no `torch`) — confirmed by dependency resolution: adding `flashrank` resolved against already-satisfied dependencies and added only 1 new package end to end, keeping the "avoid dependency bloat" principle intact while still using a purpose-built, benchmarked cross-encoder rather than reinventing scoring logic.

## Alternatives Considered

- **LLM-as-reranker via the existing Ollama client** — rejected as the *default*: lower measured retrieval quality than a purpose-built cross-encoder, meaningfully higher per-query latency (an LLM call per rerank vs. millisecond-scale ONNX inference), and fragile output parsing. Not ruled out as a *future* alternative reranking backend — the optional `rerank` flag's implementation is isolated in one function, so swapping/adding backends later doesn't require touching the endpoint contract.
- **`sentence-transformers` `CrossEncoder` (e.g. BGE-reranker-v2-m3 or `ms-marco-MiniLM-L-6-v2` directly)** — rejected: `sentence-transformers` pulls in `torch`, a heavy dependency (GPU/CPU wheel, hundreds of MB) disproportionate to this project's current scale and the "avoid dependency bloat" rule, for marginal quality gain over FlashRank's ONNX-based scoring of the same underlying model family.
- **No reranking (skip ERP-015's core mechanism)** — not viable: the ticket exists specifically to add this capability; making it optional (see Decision) already addresses the "keep it additive, don't force the cost on every request" concern without abandoning the feature.

## Consequences

One new dependency, `flashrank`, added via `uv add` (confirmed lightweight — no `torch`, minimal transitive footprint). Reranking downloads a small ONNX model file on first use (cached locally after that), similar in spirit to how Ollama pulls model weights on first use — not a paid API call. When `rerank=false` (the default), behavior and latency are identical to ERP-014's hybrid retrieval; opting in adds local CPU inference latency proportional to the number of fused candidates reranked (bounded by `top_k`, itself bounded to 50).
