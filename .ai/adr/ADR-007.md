# ADR-007 — PageIndex-Style Retrieval: Section-Sibling Expansion

Status: Accepted
Related Ticket: ERP-016

## Context

ERP-016 is the third and last of the ERP-012 follow-ups: a structure-aware retrieval mode using chunks' existing `section_path: list[str]` metadata (each chunk's full heading hierarchy, e.g. `["Chapter 2", "Background"]`, produced by ingestion's Markdown chunker). The reference "PageIndex" approach (as described in current RAG literature) builds an explicit hierarchical tree index over a document's table of contents and uses reasoning (often LLM-driven) to search that tree for the most relevant node/subtree, rather than retrieving isolated flat chunks.

This repository's data model doesn't build or persist an actual tree: `section_path` is a flat, denormalized list stored per chunk, with no parent/child linkage table. Building a real tree index (parsing `section_path`s into a shared tree structure, persisting it, and adding tree-search/traversal logic, possibly LLM-driven per the original PageIndex approach) would be a substantially larger, higher-risk change than the other two follow-ups (ERP-014, ERP-015), and does not have decided requirements (e.g. what "reasoning-based traversal" should look like, and whether an LLM call per query is acceptable latency/cost, similar to the LLM-as-reranker trade-off already rejected in ADR-006 for that reason).

## Decision

Implement a lighter-weight, additive **section-sibling expansion**: after `service.search`'s existing hybrid retrieval (+ optional reranking) produces a ranked list of chunks, an opt-in `expand_sections: bool` flag on `RetrievalQuery` triggers, for each ranked chunk ("anchor"), a lookup of every other chunk in the same document whose `section_path` is *exactly equal* to the anchor's — i.e., the anchor's full section, not just adjacent chunks. Sibling chunks not already present in the results are inserted immediately after their anchor (grouped by section, chunk-index order within the group), inheriting the anchor's score so relevance ranking-by-section is preserved. This directly uses `section_path` structure (matching the "PageIndex-inspired" theme named in `docs/architecture.md`) without requiring a new tree data structure, a new dependency, or an LLM call per query.

Equality is checked in Python (fetch all of a document's chunks by the already-indexed `document_id`, then filter by list equality) rather than as a SQL `WHERE section_path = ...` predicate, because `chunks.section_path` is a Postgres `json` column (not `jsonb`) and the `json` type has no equality operator in Postgres — comparing in Python avoids a brittle text-cast comparison and a schema/column-type change that would be out of scope here.

## Alternatives Considered

- **A real hierarchical tree index with reasoning-based traversal (the original PageIndex design)** — rejected for this ticket: needs a new persisted tree structure and a traversal/reasoning strategy (LLM-driven or heuristic) with no settled design, making it a much larger change than the ERP-012 follow-ups' established "additive, one ranking-algorithm-change-at-a-time" pattern. Left as a possible future, larger redesign if actually needed.
- **Weighted section-level score aggregation (boost a chunk's score based on how many of its section-siblings also matched)** — rejected: conflates ranking (what order to return results in) with retrieval (what to return), and would change `RetrievedChunk.score`'s meaning yet again without a clear benefit over simply surfacing the sibling chunks so the caller/generator has full section context.
- **Changing `section_path` to a SQL-comparable type (`jsonb`) to support a database-side equality/containment query** — rejected: an unnecessary schema/migration change for a comparison that's cheap enough in Python at this project's per-document chunk-count scale, and touching the column type used by two other already-merged/in-review tickets (ERP-011, ERP-014) is unwarranted scope creep here.

## Consequences

`expand_sections=True` can grow the response beyond `top_k` (it appends section context, it does not replace or re-truncate the ranked list) — documented explicitly as intended, not a bug. Latency cost is one extra per-document chunk fetch per unique document among the results (indexed by `document_id`, cheap at current scale). If a real tree-based PageIndex implementation is wanted later, this ticket's `expand_sections` flag and `RetrievedChunk` shape don't need to change — a future traversal strategy could be swapped in behind the same flag.
