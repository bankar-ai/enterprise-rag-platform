# ADR-002 — Branch Strategy & CI Approach

Status: Accepted
Related Ticket: ERP-006

## Context

The repository had no `.github/` setup at all: only `develop` existed on the remote, there was no `main` branch, no CI, and no PR template. Before real feature development starts, the repo needs a stable branch model and a baseline CI signal — but `pyproject.toml` has no dependencies yet and no linting/type-checking/testing tools are configured (that configuration is planned separately as ERP-007).

## Decision

Adopt a two-branch model: `main` as the protected, default/release branch, and `develop` as the ongoing integration branch. Feature branches merge into `develop`; `develop` merges into `main` at release points.

Introduce CI now as a minimal skeleton workflow (`uv sync` plus a `pytest` step against the existing `tests/` directory) rather than waiting for ERP-007. Lint and type-check steps are deliberately omitted until ERP-007 adds ruff/mypy as real dependencies, so the workflow doesn't reference tools that don't exist yet.

## Alternatives Considered

- **`develop`-only, no `main`** — rejected: simpler for a solo/early-stage project, but leaves no stable branch to point releases or protection rules at as the project grows.
- **Do full tooling configuration (ERP-007: ruff, mypy, pytest, pre-commit) together with CI in this same piece of work** — rejected: conflates two separate concerns and delays having any CI signal at all until the tooling ticket lands; the skeleton can be extended in place once ERP-007 exists.

## Consequences

CI will initially only run `uv sync` and `pytest` — it won't catch style or type issues until ERP-007 adds ruff/mypy and the workflow is updated to call them. Branch protection rules and setting `main` as the GitHub default branch require `gh auth login` (interactive) to be completed by the user before they can be applied via the `gh` CLI.
