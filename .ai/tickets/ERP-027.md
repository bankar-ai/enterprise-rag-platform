# ERP-027 — Admin User Management

Status: Done
Depends On: ERP-026

## Description

Adds the admin-facing user-management API surface named as a deferred follow-up in ERP-026: list users, enable/disable a user's account, and force-revoke a user's active sessions. Closes the "Admin user-management endpoints" item from `.ai/memory/current-state.md`'s Next Planned Work.

## Acceptance Criteria

- [x] `GET /admin/users`, `PATCH /admin/users/{user_id}`, `POST /admin/users/{user_id}/revoke-sessions` implemented, all gated by `require_role("admin")`
- [x] `users` table gains a required `is_active` column (default `true`) via Alembic migration; empty autogenerate diff confirmed against real Postgres
- [x] Disabling a user blocks new logins (`403`) and refresh-token rotation (`403`) immediately; an already-issued access token is not checked per-request and rides out its own ≤30 min expiry (accepted trade-off, confirmed with user)
- [x] Force-revoking sessions bulk-marks a user's refresh tokens revoked in Postgres (DB-authoritative, no per-token cache writes)
- [x] Unknown `user_id` returns `404` on both the disable and revoke-sessions endpoints; non-admin caller returns `403`; no token returns `401`
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass (262 passed, 98.97% coverage)

## Notes

Design classified as Bounded (brainstorming skill) — existing `app/auth/` module, `require_role` dependency already scaffolded in ERP-026 for this exact purpose. No design spec file; short design agreed in chat.

Still deferred (unchanged from ERP-026): admin cross-user data visibility (no elevated-privilege bypass on ownership checks), self-service admin account creation (admins are still created via direct DB insert), external IdP/OAuth2/OIDC.
