# ERP-015 — Reranking

Status: In Progress
Depends On: ERP-014

## Description

Adds an optional cross-encoder reranking pass over the fused BM25+vector candidate list ERP-014 produces. Uses FlashRank (`ms-marco-TinyBERT-L-2-v2`, ONNX, no `torch`) — see `.ai/adr/ADR-006.md` for the researched comparison against LLM-as-reranker and `sentence-transformers`-based alternatives. Additive and optional: `POST /retrieval/query` gains a `rerank: bool = false` request field; when omitted/false, behavior is identical to ERP-014's hybrid retrieval. Second of three deferred ERP-012 follow-ups: BM25 hybrid retrieval (ERP-014, done) → reranking (this ticket) → PageIndex-style structure-aware retrieval (ERP-016).

## Acceptance Criteria

- [x] New dependency `flashrank` added via `uv add`, justified in `.ai/adr/ADR-006.md` (no `torch`, minimal transitive footprint — confirmed by lockfile diff)
- [x] `RetrievalQuery` gains `rerank: bool = False`; existing requests without the field behave exactly as before (backward-compatible default)
- [x] A `Reranker` protocol + `FlashRankReranker` implementation, injectable into `service.search` the same way `embedding_client`/`faiss_index` already are
- [x] When `rerank=True`, `service.search` reranks the fused candidate list (query against each candidate's `text`) and returns results in reranker-score order; `RetrievedChunk.score` reflects the reranker's score
- [x] When `rerank=False` (default), no reranker is constructed or invoked — zero added latency/cost for callers who don't opt in
- [x] Empty candidate list reranks to an empty list without invoking the model
- [x] All new/modified modules covered by tests meeting the 90% coverage gate; the reranker is exercised for real in at least one test (small local ONNX model, no network/API mocking needed) and mocked/injected elsewhere for speed and determinism

## Notes

PageIndex-style retrieval (ERP-016) is out of scope here and layers on top of this ticket's output.
