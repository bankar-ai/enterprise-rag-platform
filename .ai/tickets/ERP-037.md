# ERP-037 — Verify and Execute Chosen Deployment Infrastructure

Status: Backlog
Depends On: ERP-034, ERP-035

## Description

`D:\github-projects\infrastructure-options.md` (see ADR-008) records the researched hosting/infra
options for making this RAG platform reachable for a bounded 2-3 month test window (5-20 users max).
The current leading choice is GCP's Always Free `e2-micro` VM (permanently free, no expiration) for
app + FAISS-index hosting, with Render Starter (~$7/mo) as a paid fallback if `e2-micro`'s modest
specs (shared vCPU, ~1GB RAM) can't reliably run FastAPI + FAISS. Neon (Postgres), Upstash (Redis),
and Modal (serverless GPU for Ollama generation/embedding) are already decided with higher
confidence. This ticket is the actual verification-and-execution pass, not just the research.

## Acceptance Criteria

- [x] Live-test the app (FastAPI + FAISS index files, no bundled Postgres/Redis) actually running on
      a GCP `e2-micro` instance under light concurrent load representative of 5-20 sporadic users;
      fall back to Render Starter if it doesn't hold up
- [x] ERP-034 (default generation model tag fix) and ERP-035 (hardware sizing doc) are resolved
      before this ticket deploys anything live, so the deployed instance doesn't hit the same
      model-not-found or OOM failures found during local verification
- [x] Real secrets generated fresh for the deployed instance (`AUTH_JWT_SECRET_KEY`, OIDC client
      secret if enabled, DB credentials) — never the local dev values
- [x] Reverse proxy + TLS in front of the deployed FastAPI app
- [x] `docker-compose.yml` (or equivalent) services set to restart automatically on failure/reboot
- [x] Modal endpoint wired in for generation/embedding, confirmed reachable from the deployed app
- [x] Neon and Upstash connection strings configured and confirmed reachable from the deployed
      instance's network/region
- [ ] Smoke-tested at ~10-20 simulated concurrent requests before calling this done
- [x] Teardown steps documented (what to delete/cancel when the 2-3 month window ends) so walking
      away is a checklist, not a guess

## Notes

This ticket intentionally does not re-litigate the *choice* of provider — that's recorded in
ADR-008 and the shared infra doc. It only covers verifying the chosen option actually works and
executing the deployment. If live-testing reveals `e2-micro` doesn't hold up, update the shared doc's
status for that row (`Needs exploration` -> ruled out or reconsidered) rather than silently switching
without recording why.

**Progress (2026-09-10)**: `e2-micro` confirmed GO (real memory headroom verified live, not
assumed — see the ERP-035-adjacent lazy-docling-import fix below). Full stack deployed and
verified end-to-end against real infrastructure, not fakes/mocks:

- GCP `e2-micro` VM (`rag-platform-host`, `us-central1-a`), `rag-platform.service` under systemd
  (`enabled`, `Restart=on-failure`) -- the `docker-compose.yml`-equivalent auto-restart criterion
  is met via systemd instead of Docker, a deliberate deviation: the VM's ~958MB RAM doesn't have
  headroom for the Docker daemon's own overhead on top of the app, so the app runs directly via
  `uv run uvicorn`, not in a container. See `docs/deployment.md` and
  `D:\github-projects\gcp-deployment-tracker.md`.
- Caddy reverse proxy with real Let's Encrypt TLS via a free `sslip.io` hostname (no purchased
  domain) -- `https://34-31-5-88.sslip.io`, confirmed `200` from an external client.
- **A real bug found and fixed via this live-testing, not caught by any test suite**: `docling`
  (an ingestion *fallback* path, rarely reached) was imported eagerly at module level in
  `app/ingestion/parsers.py`, forcing every process start to pay its `torch`/`transformers` import
  cost (~500MB+ resident) regardless of whether it's ever used. Made lazy (import moved inside
  `parse_quality()`); cut the app's baseline memory roughly in half (509MB -> 268MB RSS), which is
  what made `e2-micro` viable at all. See the `perf: lazy-import docling` commit.
- Neon (Postgres) and Upstash (Redis) both provisioned and verified with real traffic, not just
  connectivity checks: `POST /auth/register` returned `201` with a real persisted user row;
  `POST /auth/login` -> `POST /auth/refresh` both returned `200`, exercising the Redis-backed
  refresh-token revocation cache for real. Full details, including the exact env var names each
  of the three separate Redis-consuming settings classes needs (`EMBEDDING_REDIS_URL`,
  `RETRIEVAL_REDIS_URL`, `AUTH_REDIS_URL` -- there is no single `REDIS_URL`), in the tracker doc.
- Modal: a new `deploy/modal_ollama.py` serves Ollama (`gemma3:4b` + `nomic-embed-text`, baked into
  the image at build time) as a public HTTPS endpoint speaking Ollama's native API directly, so
  `OllamaLLMClient`/`OllamaEmbeddingClient` needed zero code changes -- just pointing
  `GENERATION_OLLAMA_HOST`/`EMBEDDING_OLLAMA_HOST` at it. Two real deployment bugs found and fixed
  along the way (not obvious from any reference example, verified by actually deploying, not
  assumed): the reference tutorial's hardcoded `ollama-linux-amd64.tgz` download URL is stale
  (Ollama repackaged to `.tar.zst` since), and Ollama binds `127.0.0.1` by default, invisible to
  Modal's reverse proxy, requiring `OLLAMA_HOST=0.0.0.0:11434` set explicitly.
- **Full pipeline verified end-to-end on the live deployment**: a real chunk ingested via
  `embed_and_persist`, retrieved via `search()`, and answered correctly and grounded via the live
  Modal endpoint -- "The Eiffel Tower is located in Paris, France [1]."

**Remaining for this ticket**: the ~10-20 simulated concurrent request smoke test (acceptance
criterion 8) has not been run yet -- everything verified so far has been correctness/connectivity
checks at low (single-request) concurrency, not a load test.
