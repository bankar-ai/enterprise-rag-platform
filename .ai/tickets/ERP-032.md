# ERP-032 — External IdP / OAuth2 / OIDC Integration

Status: Done
Depends On: ERP-026

## Description

ERP-026 shipped local email/password authentication as the v1 identity model, with external IdP/OAuth2/OIDC integration explicitly deferred. Local-only auth has no SSO story, which blocks enterprise adoption (no Google/Microsoft/Okta login, no centrally-managed identity/offboarding). This ticket adds OIDC-based login as an additional authentication path alongside (not replacing) local email/password.

## Acceptance Criteria

- [x] Users can authenticate via at least one external OIDC provider (e.g. Google, Microsoft Entra ID, or a generic OIDC-compliant provider — provider choice to be confirmed with the user)
- [x] Existing local email/password login (`POST /auth/login`) continues to work unchanged
- [x] OIDC-authenticated users get/reuse the same `users` table and JWT access/refresh-token issuance as local auth, so every existing per-user isolation and role check (ERP-026, ERP-027) applies unchanged
- [x] Account linking behavior for an email that exists in both local and OIDC form is explicitly decided and documented (not left as undefined behavior)
- [x] No new dependency introduced without prior approval, per CLAUDE.md's Dependency Policy
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Implemented via Authlib (`joserfc` for JOSE/JWKS/ID-token verification) as a provider-agnostic OIDC Authorization Code + PKCE client, config-driven from `AuthSettings` (issuer/client ID/secret/redirect URI resolved at request time from the issuer's `.well-known/openid-configuration` discovery document — no Google-specific code anywhere). Google is the reference/test provider (approved in the ticket brief; free, no new self-hosted infra).

New endpoints: `GET /auth/oidc/{provider}/login` (307 redirect to the IdP) and `GET /auth/oidc/{provider}/callback` (200 JSON, returns the same `access_token`/`refresh_token` pair local login issues — no frontend exists in this repo to redirect back to). `POST /auth/login`/`register`/`refresh`/`logout` are byte-for-byte unchanged.

**Data model**: a new `oidc_identities` table (`user_id`, `provider`, `external_id`, `email`, unique on `(provider, external_id)`) rather than columns on `users` directly, so one user can hold a local password and one or more linked OIDC identities at once. `users.hashed_password` is now nullable (OIDC-only users have none). Migration `dd26f4e8c54f`, verified upgrade/downgrade both directions with an empty autogenerate diff after upgrading.

**Account linking decision**: an OIDC login whose email matches an existing user is auto-linked only when the ID token asserts `email_verified: true`; otherwise it's rejected with `409 Conflict`, creating nothing. Rationale and full detail in the design spec's "Account Linking Decision" section — this is what prevents an attacker who controls an OIDC identity with an unverified claim to someone else's email from taking over that person's existing account.

**Security self-review caught and fixed a real design flaw pre-merge**: the first draft carried the PKCE `code_verifier`/`nonce` inside the OAuth `state` query parameter (reasoning: no server session). This was wrong on two counts — it put the verifier in the same URL-visible channel as the authorization `code` (defeating PKCE's purpose against anyone who can read that URL, including ordinary access logs), and it had no per-browser binding at all, allowing a classic login-CSRF (an attacker completes their own OIDC login and CSRFs the resulting `code`/`state` into a victim's browser). Fixed by moving the verifier/nonce into a short-lived `HttpOnly`/`Secure`/`SameSite=Lax` cookie (`oidc_state`, scoped to `/auth/oidc`), with `state` reduced to a plain opaque anti-CSRF token checked against the cookie's own embedded `state` claim. See `docs/superpowers/specs/2026-09-06-oidc-authentication-design.md`'s "State/PKCE/nonce" section.

Dependencies: `authlib` (pre-approved) and `httpx` (promoted from a transitive dev dependency to a direct one, since `app/auth/oidc.py` now imports it for discovery/token-exchange HTTP calls).

Tests (`tests/auth/test_oidc.py` new; additions to `test_repository.py`/`test_service.py`/`test_router.py`/`test_config.py`) never perform a real network call — `httpx.MockTransport` fakes discovery/JWKS/token-exchange HTTP, and ID token signature verification is exercised against a real in-test-generated RSA keypair rather than a real IdP's key. Verified: `ruff check .` clean, `mypy --strict app` clean, full suite (347 tests) passing with coverage above the 90% gate.

Deferred/known limitations: only Google is verified as a concrete reference provider — generic-provider support beyond Google is exercised only against the OIDC/JWKS protocol spec, not a second real IdP. No self-service "link this OIDC identity to my existing logged-in account" flow exists; a rejected conflict simply means the user keeps using their existing login method.
