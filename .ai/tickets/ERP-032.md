# ERP-032 — External IdP / OAuth2 / OIDC Integration

Status: Backlog
Depends On: ERP-026

## Description

ERP-026 shipped local email/password authentication as the v1 identity model, with external IdP/OAuth2/OIDC integration explicitly deferred. Local-only auth has no SSO story, which blocks enterprise adoption (no Google/Microsoft/Okta login, no centrally-managed identity/offboarding). This ticket adds OIDC-based login as an additional authentication path alongside (not replacing) local email/password.

## Acceptance Criteria

- [ ] Users can authenticate via at least one external OIDC provider (e.g. Google, Microsoft Entra ID, or a generic OIDC-compliant provider — provider choice to be confirmed with the user)
- [ ] Existing local email/password login (`POST /auth/login`) continues to work unchanged
- [ ] OIDC-authenticated users get/reuse the same `users` table and JWT access/refresh-token issuance as local auth, so every existing per-user isolation and role check (ERP-026, ERP-027) applies unchanged
- [ ] Account linking behavior for an email that exists in both local and OIDC form is explicitly decided and documented (not left as undefined behavior)
- [ ] No new dependency introduced without prior approval, per CLAUDE.md's Dependency Policy
- [ ] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Needs a design/brainstorming pass to pick the specific IdP(s) to support and the OIDC library (if any) — research current Python OIDC client options before recommending one, per CLAUDE.md's "Research Before Recommending" rule. Also needs a decision on whether this closes or narrows ERP-026's other deferred item, "self-service admin account creation" (an OIDC group/claim could plausibly gate initial admin assignment) — worth revisiting once this ticket is scoped.
