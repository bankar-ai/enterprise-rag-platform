# ERP-019 — Conversation History Read Endpoint

Status: Done
Depends On: ERP-018

## Description

Adds `GET /conversations/{conversation_id}`, the read-side companion to ERP-018's stateful `POST /generation/query` flow — deferred (not abandoned) in that ticket's design spec. Returns a conversation's full message history, oldest first, so a client can reload a conversation (e.g. after a page refresh) without having cached every turn locally. Brainstormed as a bounded task (small, well-scoped addition to code that already exists); no separate design spec was written.

## Acceptance Criteria

- [x] `app/generation/repository.py` gains `get_conversation` (plain lookup, no create-on-miss — distinct from `get_or_create_conversation`, which must not be used on a read path) and `get_all_messages` (unlimited, oldest-first, unlike the windowed `get_recent_messages`)
- [x] `app/generation/schemas.py` gains `Message` (`role`, `content`, `created_at`) and `ConversationHistoryResponse` (`conversation_id`, `messages: list[Message]`)
- [x] `app/generation/service.py` gains `get_conversation_history(conversation_id) -> ConversationHistoryResponse | None`, returning `None` for an unknown ID
- [x] `GET /conversations/{conversation_id}` on a new top-level `conversations_router` (prefix `/conversations`, separate from the existing `/generation` router — a conversation is its own resource) registered in `app/main.py`; returns `200` with full history, or `404` for an unknown ID
- [x] All new/modified modules covered by tests meeting the 90% coverage gate

## Notes

Full history, no pagination — conversations are expected to be small at this platform's current scale, and the use case (reload after refresh) needs everything the client had, not a windowed slice. Pagination was considered and explicitly deferred as premature.

404 (not 200-with-empty-list) for an unknown ID was a deliberate choice, distinct from `POST /generation/query`'s lenient get-or-create semantics — a GET is retrieving something, not implicitly creating it, and 404 lets a client distinguish "valid but empty" (doesn't happen in practice, since `generate()` always creates the conversation and its first two messages together) from "this ID was never used."

Full suite: 161 tests, 99.59% coverage (gate: 90%), mypy clean, ruff clean.
