# ERP-012 — Semantic Retrieval Endpoint

Status: In Progress
Depends On: ERP-011

## Description

Adds the first retrieval slice: a synchronous `POST /retrieval/query` endpoint that embeds a query, searches the FAISS index built by ERP-011, hydrates matching chunks from Postgres, and returns them ranked by similarity. Scoped to vector-only search — BM25/hybrid retrieval, reranking, and PageIndex-style structure-aware retrieval are explicitly deferred as additive follow-ups, not redesigns of this endpoint's contract. See `docs/superpowers/specs/2026-08-08-retrieval-endpoint-design.md` for the design and `docs/superpowers/plans/2026-08-08-retrieval-endpoint.md` for the implementation plan.

## Acceptance Criteria

- [ ] `FaissIndex.search(vector, k)` returns nearest `(vector_id, distance)` pairs, nearest-first
- [ ] `app/ingestion/repository.py` gains `get_chunks_by_vector_ids` for hydrating FAISS hits back into full chunk rows
- [ ] New `app/retrieval/` module: `schemas.py` (`RetrievalQuery`, `RetrievedChunk`, `RetrievalResponse`), `service.py` (`search`), `router.py` (`POST /retrieval/query`)
- [ ] Empty index returns `200` with empty results, not an error
- [ ] `top_k` validated (default 5, bounded 1-50); empty query rejected with 422
- [ ] Router registered in `app/main.py`
- [ ] All new/modified modules covered by tests meeting the existing 90% coverage gate; embedding calls mocked, DB/FAISS tests run for real

## Notes

Follows the same incremental vertical-slice pattern as ingestion (ERP-*) and embedding/persistence (ERP-011). BM25 (via Postgres full-text search), reranking, and PageIndex-style retrieval are deliberately out of scope — see the design spec's Context section for why each is additive rather than a rework of this slice.
