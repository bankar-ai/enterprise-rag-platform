# ERP-022 — Harden Redis Cache Clients & Revisit Retrieval Cache Key Scoping

Status: Done
Depends On: ERP-013, ERP-021

## Description

Two follow-ups surfaced by ERP-021's final whole-branch review, deliberately left out of that branch's scope:

1. **Harden both Redis-backed cache clients.** ERP-021's final review found three gaps in `app/retrieval/cache.py`'s `RedisRetrievalCache`, all fixed on that branch: no socket connect/read timeouts (a hanging/unroutable Redis blocks the caller for the OS TCP timeout instead of failing fast), a fresh `redis.Redis` client/connection pool constructed on every call instead of memoized, and cache-value deserialization sitting outside the `except redis.RedisError` guard (a corrupt or schema-stale cached entry raises instead of degrading to a miss, breaking ADR-003's "never load-bearing" guarantee). `app/embedding/cache.py`'s `RedisEmbeddingCache` (ERP-013) has the identical three gaps and was explicitly left unfixed, since it was out of ERP-021's file scope. Apply the same three fixes there: `socket_connect_timeout`/`socket_timeout` on the client (via a new `EmbeddingSettings` field, mirroring `RetrievalSettings.redis_socket_timeout_seconds`), an `lru_cache`-wrapped default-client factory (mirroring `get_default_retrieval_cache()`), and a `try/except (ValueError, UnicodeDecodeError)` around the `json.loads` deserialization step in `get()`.

2. **Revisit the retrieval cache key once authentication exists.** `app/retrieval/service.py`'s `_cache_key` (ERP-021) hashes `query`, `top_k`, `rerank`, and `expand_sections` only — no user or tenant identity. Correct today, since there is no auth system and no per-document access control. Once a future Authentication ticket adds per-document permissions, this becomes a cross-user data-leak vector: user A's cached results could be served to user B under an identical query string, even if B lacks permission to see some of the underlying documents. Revisit the cache key (and/or cache scoping) as part of that Authentication ticket, not before — there's nothing meaningful to build here until permissions exist.

## Acceptance Criteria

- [x] `app/embedding/config.py`'s `EmbeddingSettings` gains a socket-timeout field (`EMBEDDING_`-prefixed, mirroring `RetrievalSettings.redis_socket_timeout_seconds`'s name/default/shape)
- [x] `RedisEmbeddingCache.__init__` passes `socket_connect_timeout`/`socket_timeout` into `redis.Redis.from_url(...)`
- [x] `app/embedding/cache.py` gains an `lru_cache`-wrapped `get_default_embedding_cache()` factory; `OllamaEmbeddingClient`'s default-construction path uses it instead of constructing `RedisEmbeddingCache(settings)` inline
- [x] `RedisEmbeddingCache.get()`'s `json.loads(raw)` call is wrapped in `try/except (ValueError, UnicodeDecodeError)`, degrading to `None` on failure (logged), matching `RedisRetrievalCache.get()`'s pattern
- [x] All changes covered by tests meeting the existing 90% coverage gate, mirroring the equivalent `RedisRetrievalCache` tests added in ERP-021
- [x] Item 2 (cache-key scoping) is NOT implemented here — it's recorded as a note/dependency on the future Authentication ticket, to be actioned there

## Notes

Both items originate from the final whole-branch review of ERP-021 (`docs/superpowers/plans/2026-09-04-retrieval-query-cache.md`'s SDD execution) — see that PR (#18) for the original finding text and the equivalent fixes already applied to `app/retrieval/cache.py`.
