# ERP-018 — Conversation Memory

Status: Done
Depends On: ERP-017

## Description

Makes `POST /generation/query` (ERP-017) multi-turn. Adds an optional `conversation_id` that acts as a stateless/stateful switch: omitted, the endpoint behaves byte-for-byte as it did under ERP-017 (no DB session opened, nothing persisted); provided, it's a client-supplied UUID with get-or-create semantics — the server persists both turns of the exchange to two new Postgres tables and, from the second turn onward, rewrites the follow-up query into a standalone form (via the existing LLM client) before handing it to retrieval, so a question like "what about the second one?" resolves against what was actually discussed. See `docs/superpowers/specs/2026-09-01-conversation-memory-design.md` for the full design and `docs/superpowers/plans/2026-09-01-conversation-memory.md` for the implementation plan.

## Acceptance Criteria

- [x] New `conversations` (`id: UUID` primary key, client-supplied, never server-generated; `created_at`) and `conversation_messages` (`id`, `conversation_id` FK, `role`, `content`, `created_at`, `sequence`) tables in `app/generation/models.py`, sharing the existing `Base` from `app/ingestion/models.py`; new Alembic migration(s)
- [x] `app/generation/repository.py` — `get_or_create_conversation`, `append_message`, `get_recent_messages`, mirroring `app/ingestion/repository.py`'s style; tested against a real Postgres test database
- [x] `app/generation/rewrite.py` — `rewrite_query(query, history, llm_client)`, reusing the existing `LLMClient`/model (no separate rewrite-model setting); only invoked when history is non-empty
- [x] `GenerationQuery.conversation_id: UUID | None = None`; `GenerationResponse.conversation_id: UUID | None` (`null` when the call was stateless, otherwise echoed/created ID)
- [x] `GenerationSettings.history_window_turns: int = 6` bounds how much history is loaded/rendered
- [x] `app/generation/prompt.py`'s `build_prompt` gains an optional `history` parameter, rendered before the numbered context block, chronological order
- [x] `service.generate` implements the full stateless/stateful flow: no `conversation_id` → ERP-017's unchanged path; `conversation_id` given → load history, rewrite if history non-empty, retrieve, generate, persist both turns in one transaction only after generation succeeds (including the empty-retrieval short-circuit case, which still persists)
- [x] No "unknown ID" error case — any client-supplied ID is valid to start or continue a conversation; router keeps ERP-017's exact `200`/`503` outcomes, no new exception-to-status mapping
- [x] All new/modified modules covered by tests meeting the 90% coverage gate

## Notes

`GET /conversations/{id}` and streaming responses remain explicitly out of scope (deferred, not abandoned — the design spec names both as candidates for future tickets once a real client needs them). Authentication/ownership of conversations is a separate, not-yet-built roadmap item; a `conversation_id` is a bearer capability with no ownership check, by deliberate design (see the spec's Context section).

Two mid-implementation plan-text defects were found and fixed during this ticket, both re-verified by task reviewers — see `.ai/sessions/2026-09-01-conversation-memory.md` for details:
- A non-deterministic message-ordering bug traced to `now()` being the transaction-start timestamp, fixed by adding a monotonic `sequence` column.
- An under-counted number of LLM calls in the plan's literal router test code, fixed by extending the test fixture (no production-code change).

Full suite: 149 tests, 99.57% coverage (gate: 90%), mypy clean, ruff clean. See `.ai/sessions/2026-09-01-conversation-memory.md` for the brainstormed design decisions and full commit list.
