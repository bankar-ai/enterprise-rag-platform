# ERP-034 — Fix Default Generation Model Tag Mismatch

Status: Backlog
Depends On: None

## Description

`GenerationSettings.model` (`app/generation/config.py`) defaults to `"qwen3"`. Ollama only resolves
an untagged model name to an implicit `:latest` tag; it does not fall back to any other tag a user
happens to have pulled. Verified live against a real local Ollama install with `qwen3:8b` (not
`qwen3:latest`) installed:

```
ollama.chat(model="qwen3", ...) -> {"error": "model 'qwen3' not found"}
```

`POST /generation/query` and `POST /generation/query/stream` both 500 on a fresh deployment unless
the operator already knows to set `GENERATION_MODEL` to their exact installed tag -- and that env
var is undocumented today (`.env.example` has no entry for it, unlike the required
`AUTH_JWT_SECRET_KEY`).

## Acceptance Criteria

- [ ] `.env.example` documents `GENERATION_MODEL` (and `EMBEDDING_MODEL` if it has the same gap)
      with a comment explaining Ollama's exact-tag resolution behavior and an example matching a
      real `ollama pull` tag (e.g. `qwen3:8b`)
- [ ] Decide and implement one of: (a) fail fast at startup with a clear error if the configured
      model isn't present in `ollama list`/`ollama show`, rather than failing on the first user
      request, or (b) keep the current default but make the startup-time requirement explicit in
      logs
- [ ] `docs/architecture.md` or a new deployment doc notes that the model tag must match exactly
      what was pulled locally
- [ ] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Found during a live "does this actually work when we make it live" verification session
(2026-09-07): confirmed via direct Ollama API call and via the `app.generation.client.OllamaLLMClient`
code path both failing identically with the default config against a real installed model.
