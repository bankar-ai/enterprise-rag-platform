# ERP-024 — Declare `search_vector`'s GIN Index on the ORM Model

Status: Done
Depends On: None

## Description

ERP-014's GIN index backing full-text search (`ix_chunks_search_vector`, on `chunks.search_vector`) exists only in the Alembic migration (`a97a8780506f`), not in SQLAlchemy's `Base.metadata`. `app/ingestion/models.py`'s `ChunkRecord.search_vector` column has no matching `Index(...)` declaration. This means anything that bootstraps schema via `Base.metadata.create_all` (the test suite, per `tests/conftest.py`) creates the `search_vector` column but never the index backing it — so `search_chunks_by_text`'s full-text-search tests exercise a sequential scan, not the indexed path Postgres actually uses in any environment provisioned via `alembic upgrade head`.

## Acceptance Criteria

- [x] `app/ingestion/models.py`'s `ChunkRecord` declares a GIN index on `search_vector` (`__table_args__`, matching the migration's index name `ix_chunks_search_vector` and `postgresql_using="gin"`) so `Base.metadata.create_all` creates it too
- [x] `alembic revision --autogenerate` produces no diff for this index (model and migration now agree — confirms no drift)
- [x] Existing full-text-search tests (`tests/ingestion/test_repository.py`) still pass unmodified

## Notes

Low urgency at current scale (near-zero rows), but a real correctness/perf gap if left long-term — anything relying on `Base.metadata.create_all` for schema (tests today, potentially other tooling later) silently never exercises the indexed path.
